<Update label="1.8.1" description="2026-08-29">
## Sharper watchlist search and stricter validators

A quality release with no request or response changes. Watchlist-connected jobs
search the index in a single pass restricted to your watchlist from the start, and
validator-driven queries judge evidence more literally. Existing jobs and event monitors
pick both up automatically.

### Watchlist search is restricted from the start

A job connected to a watchlist now runs one combined index search per query,
scoped to the watchlist entities up front, instead of fetching broadly and
filtering afterwards.

- Less noise in the raw results, so fewer irrelevant articles reach your records.
- Faster completion, since the wider unrestricted fetch is no longer performed.

No changes to
[`POST /catchAll/submit`](/web-search-api/api-reference/jobs/create-job) — the
behavior applies to any job submitted with `connected_dataset_ids`. See
[Company Monitors](/web-search-api/concepts/company-monitors).

### Validators apply their criteria literally

A [validator](/web-search-api/concepts/dynamic-schemas) no longer defaults to
passing a record when the evidence is ambiguous. It now applies the validator
criteria literally to the evidence in the citation.

Expect noticeably fewer false positives on validator-driven queries such as data
breach detection. If a validator was previously passing borderline records for
you, you may now see fewer records returned — tighten or loosen the validator
description to tune it.

### Fixes and improvements

- Validator evaluation is faster and cheaper per record, with no quality
  regression in internal benchmarks.
- [`GET /catchAll/entities`](/web-search-api/api-reference/entities/list-entities)
  and [`GET /catchAll/webhooks`](/web-search-api/api-reference/webhooks/list-webhooks)
  now document the `404` returned when `project_id` doesn't reference an existing
  project, matching the other project-scoped endpoints.
</Update>

<Update label="1.8.0" description="2026-08-26">
## Source groups, event tagging, and pipeline recall improvements

Two new ways to shape what you get back: curated source groups to scope fetching
to trusted domains, and automatic event classification on watchlist results. This
release also carries a large body of pipeline work aimed at not missing obvious
events, plus a clearer split between authentication and authorization errors.

### Source groups

Source groups are named, curated domain allowlists maintained by NewsCatcher — for
example "Top 100 US Finance". Attach one to a job to scope article fetching to its
domains instead of maintaining a long domain list yourself.

- [`GET /catchAll/source-groups`](/web-search-api/api-reference/jobs/list-source-groups)
  lists the groups available to your organization, each with `slug`, `name`, and
  `description`. It covers public groups plus any restricted groups your
  organization has been granted access to.
- [`POST /catchAll/submit`](/web-search-api/api-reference/jobs/create-job) accepts
  an optional `source_groups` array of slugs. Maximum 20 per job.
- Job results echo the attached groups back as `source_groups`, and event monitor results
  do the same under `reference_job`.
- Domains resolve when the job runs, so adding or removing a domain from a group
  takes effect on every later run with no change on your side.

See [Source groups](/web-search-api/concepts/source-groups).

### Event tagging on watchlist results

Records from all-news watchlist jobs — those submitted with
`fetch_all_watchlist_news: true` — now carry a `tags` object classifying the event
with a fixed taxonomy:

- `event_type` describes what happened, as a taxonomy path such as
  `deals.merger_acquisition`.
- `sector` gives the industry, such as `banking`.

Tagging is additive and never filters results. A record the classifier cannot place
is still returned, with `unclassifiable` or `other_sector` in place of a taxonomy
value. Other job types are unaffected and return no `tags`.

See [Event tagging](/web-search-api/concepts/company-monitors#event-tagging).

### Authentication and authorization errors are now distinct

`401` and `403` now mean different things. A request whose caller cannot be
identified returns `401`; a request from an identified caller who isn't allowed
returns `403`.

- A missing, unknown, or disabled API key now returns `401 Api key not found`.
  It previously returned `403 User and organization combination not found`.
- An API key belonging to a different organization than the requested
  `x-organization-id` also returns `401`.
- An unrecognized email now returns `401 User not found` instead of `404`.
- A valid user who isn't a member of the requested organization still returns
  `403`. A member with no active API key in that organization now returns the more
  specific `403 No active API key found for user in this organization`.

If you branch on status codes, treat `401` as re-authenticate and `403` as a
permissions problem.

### Filter entities and webhooks by project

[`GET /catchAll/entities`](/web-search-api/api-reference/entities/list-entities) and
[`GET /catchAll/webhooks`](/web-search-api/api-reference/webhooks/list-webhooks)
accept the optional `project_id` query parameter, matching the job, event monitor, and
dataset lists.

### Fixes and improvements

- Fewer missed events: stronger validation and deduplication now reason about
  event identity rather than article similarity, so materially different events
  stay separate and weak records no longer contaminate merges.
- Event timeframe validation gained a ±24-hour grace window, so an event reported
  just outside an exact UTC boundary is no longer dropped. Event monitors keep their
  exact rolling window.
- Clustering compares monetary amounts, so events with materially different values
  are no longer merged, and oversized clusters are re-split.
- Precision filtering now judges relevance from real source excerpts, reducing
  false removal of relevant events.
- Extraction returns no value rather than a guessed one when the source material
  doesn't support it.
- Jobs interrupted mid-run resume from the last checkpoint instead of repeating or
  losing completed work.
- Jobs whose requested enrichment fields are almost never derivable now stop early
  and report that, rather than continuing to process. Records already produced are
  kept.
- Watchlist fetching is bounded per job to keep large watchlists predictable, and
  event monitor scheduling validates state at fire time so disabled event monitors stop
  reliably.
</Update>

<Update label="1.7.0" description="2026-08-04">
## Webhooks as project resources and search quality improvements

A quality-focused release. Webhooks become a first-class project resource,
webhook responses now return their masked auth configuration, and job listings
can be filtered by processing mode. The bulk of this release is under the hood:
recall, ranking, and clustering improvements to result quality.

### Webhooks in projects

Webhooks can now be organized into [projects](/web-search-api/concepts/projects)
alongside jobs, event monitors, and datasets.

- `resource_type` accepts `webhook` when adding resources to a project via
  [`POST /catchAll/projects/{project_id}/resources`](/web-search-api/api-reference/projects/add-resource).
- [`POST /catchAll/webhooks`](/web-search-api/api-reference/webhooks/create-webhook)
  accepts an optional `project_id` to attach a webhook to a project on creation.
  Returns `404` if the project doesn't exist and `403` if it belongs to another
  organization.
- Project overview responses include a `webhooks` total.
- Unlike other resources, a webhook can belong to several projects, and deleting
  a project never deletes its webhooks — they are detached and keep delivering,
  even with `delete_resources=true`.

### Masked auth on webhook responses

Webhook objects now include an `auth` field describing the authentication sent
with each delivery, discriminated by `type` (`bearer`, `api_key`, or `basic`).
Secret values — `token`, `value`, and `password` — are masked, so you can verify
which scheme is configured without exposing credentials. `auth` is `null` when
no authentication is set. See
[Read back the configured auth](/web-search-api/how-to/set-up-webhooks#read-back-the-configured-auth).

### Filter jobs by processing mode

[`GET /catchAll/jobs/user`](/web-search-api/api-reference/jobs/list-user-jobs)
accepts a new optional `mode` query parameter (`base` or `lite`) to return only
jobs that ran in that mode. Omit it to list jobs in both modes.

### CSV exports omit unused entity columns

CSV exports from
[jobs](/web-search-api/api-reference/jobs/get-job-results-as-csv) and
[event monitors](/web-search-api/api-reference/event-monitors/get-latest-monitor-results-as-csv)
now include the `event_associated_entities` and `mention_entities` columns only
when the job used a connected entity dataset. Previously they were always
present, often empty. If you parse exports by column position, read columns by
header name instead.

### Fixes and improvements

- Query generation reverted to a recall-first generator by default for `base`
  jobs — the previous precision-first approach was too narrow.
- New ranking formula applied both at clustering and at pull time.
- Clustering similarity threshold raised from 0.7 to 0.85, with NER-based and
  time-decay edge weighting, to stop distinct events being merged.
- Removed an enrichment timeframe filter that was incorrectly dropping valid
  records and citations.
- Beyond News: expanded domain-based fetching, percolation, and entity
  enrichment across all connected-dataset jobs.
- Event monitor scheduler moved to fully asynchronous execution.
- Fixed a gateway bug that returned "Invalid Request Received" on valid
  requests.
- Delivery history records now report `resource_type: test` for manual test
  deliveries, which aren't tied to a real resource.
</Update>

<Update label="1.6.4" description="2026-07-07">
## Custom webhook payloads and manual delivery triggers

Adds custom-formatted webhook payloads with Liquid templates and a new endpoint
to trigger webhook delivery on demand, plus search quality and coverage
improvements.

### Custom webhook payload formatting

Webhooks with `type` set to `custom` now accept a structured `formatter_config`
so you can shape the delivered request body to fit a downstream system — trim or
rename fields, apply conditional logic, or emit non-JSON formats.

- `formatter_config.template` — a [Liquid](https://shopify.github.io/liquid/)
  template string rendered at dispatch time (up to 10 KB).
- `formatter_config.content_type` — the `Content-Type` of the rendered output
  (defaults to `application/json`; also supports `text/html`, `text/plain`,
  `text/csv`, XML, and JSON-LD).

Accepted on
[`POST /catchAll/webhooks`](/web-search-api/api-reference/webhooks/create-webhook)
and
[`PATCH /catchAll/webhooks/{webhook_id}`](/web-search-api/api-reference/webhooks/update-webhook),
and returned on webhook objects. See
[Set up webhooks](/web-search-api/how-to/set-up-webhooks#custom-payload-formatting).

### Manual webhook trigger

Dispatch a webhook delivery for a resource on demand — to re-deliver after a
failed delivery or replay a past run — without waiting for the next job or
event monitor cycle.

**New endpoint:**

- [`POST /catchAll/webhook/trigger/{resource_type}/{resource_id}`](/web-search-api/api-reference/webhooks/trigger-webhook)
  — Trigger delivery for an assigned webhook, with an optional `job_id` to replay
  a specific run.

### Fixes and improvements

- More precise query generation for faster, lower-cost jobs without sacrificing
  relevance.
- Broader coverage, including support for fetching more than 10K articles per
  query and expanded Beyond News sources (podcasts included by default).
- Cleaner results through improved cluster ranking, minimum-citation thresholds,
  and low-signal cluster suppression.
- Stronger entity disambiguation and automatic entity descriptions to reduce
  same-name false positives in watchlist matching.
</Update>

<Update label="1.6.3" description="2026-06-23">
## External entity IDs, CSV exports, and connected dataset details

Adds support for your own external entity identifiers, CSV downloads for job and
event monitor results, and richer connected-dataset information in pull responses.

### External entity IDs

You can now attach your own identifier to an entity with the new
`external_entity_id` field — store a CRM, data warehouse, or internal database ID
and round-trip it through CatchAll so you can join results back to your systems
without extra mapping work. The field is a free-form string (up to 255
characters) and is not enforced as unique.

**Where it appears:**

- Accepted when creating an entity via
  [`POST /catchAll/entities`](/web-search-api/api-reference/entities/create-entity)
  and when updating one via
  [`PATCH /catchAll/entities/{entity_id}`](/web-search-api/api-reference/entities/update-entity).
- Returned on entity responses, dataset entity summaries, and connected entities
  in Company Monitors results. Null when not set.

### CSV export endpoints

Pull job and event monitor results directly as a CSV download for spreadsheet-friendly
analysis and reporting. Each row is one record, with enrichment fields as
columns, citations as a JSON column, and connected entities split into
`event_associated_entities` and `mention_entities` JSON columns.

**New endpoints:**

- [`GET /catchAll/pull/{job_id}/csv`](/web-search-api/api-reference/jobs/get-job-results-as-csv)
  — Download a completed job's results as CSV.
- [`GET /catchAll/monitors/pull/{monitor_id}/csv`](/web-search-api/api-reference/event-monitors/get-latest-monitor-results-as-csv)
  — Download the latest event monitor run's results as CSV.

### Connected dataset details in pull responses

Job and event monitor pull responses now include a `connected_datasets` array — each
entry has the dataset `id`, `name`, and an `is_deleted` flag — alongside an
`is_all_news_query` boolean indicating whether the query was submitted as an
all-news (watchlist-generic) query.

### Fixes and improvements

- Reliability and observability improvements, data-model and validation
  hardening, and language-query guardrails.
- Relaxed company domain requirements and safer enrichment handling for edge
  cases.
</Update>

<Update label="1.6.1" description="2026-06-09">
## Company Monitors improvements and performance fixes

Adds two new Company Monitors controls — association-type filtering and
all-news queries — along with performance improvements and API quality fixes.

### Association type filtering

When submitting a job connected to a dataset (watchlist), you can now set
`ed_association_type` to control how strictly tracked entities must relate to
each returned event.

- **`event_associated`** — only returns events where a tracked entity is the
  primary actor (e.g., the company that raised funding, was acquired, or
  announced layoffs). Passing references are excluded.
- **`mention`** — returns any event where a tracked entity appears, whether as
  a primary actor or a passing reference.

When omitted, no association-type filter is applied.

Each matched entity in results includes an `association_type` field indicating
how it relates to that specific record.

**New parameter:**

- `ed_association_type` on
  [`POST /catchAll/submit`](/web-search-api/api-reference/jobs/create-job)
  — Filter connected-entity results by association type. Requires
  `connected_dataset_ids`.

### All-news watchlist queries

You can now submit a connected job without specifying a topic query. Set
`fetch_all_watchlist_news: true` to retrieve all news for the entities in your
connected watchlist — no topic required. Wildcard queries (`*`) and generic
phrases like "all news" also trigger this behavior.

Event monitors created from an all-news job preserve the behavior: each recurring run
collects all news for the connected watchlist, not topic-restricted results.

`fetch_all_watchlist_news` without `connected_dataset_ids` returns a validation
error.

**New parameters:**

- `fetch_all_watchlist_news` on
  [`POST /catchAll/submit`](/web-search-api/api-reference/jobs/create-job)
  — When `true`, retrieves all news for connected watchlist entities without
  topic filtering. Requires `connected_dataset_ids`.
- `fetch_all_watchlist_news` on
  [`POST /catchAll/initialize`](/web-search-api/api-reference/jobs/initialize-job)
  — Preview validators and enrichments for an all-news watchlist query. Also
  accepts `connected_dataset_ids`.

### Fixes and improvements

- **Performance**: Faster percolation queries, reduced Elasticsearch pressure,
  and lower HTTP client concurrency for more stable throughput under load.
- **API correctness**: Schema type cleanup and enum-based job-status retrieval.
  Improved OpenAPI spec to enable automated SDK generation.
- **Project deletion**: Better notification handling and improved response
  structure when deleting a project with resources.

</Update>

## Centralized webhooks, query validation, and projects

Introduces centralized webhook management to replace per-event-monitor inline
configuration, a pre-submission query validation endpoint, and projects for
organizing and sharing resources.

### Centralized webhooks

Replaces the `webhook` inline field on event monitor creation and update with a
reusable, resource-agnostic webhook system.

**Features:**

- **Webhook management**: Create named webhook endpoints at the organization
  level and reuse them across any number of jobs or event monitors.
- **Flexible assignment**: Pass `webhook_ids` at job or event monitor creation time,
  or assign webhooks after creation. Each resource supports up to 5 webhooks.
- **Delivery modes**: `full` sends all records in a single request per trigger.
  `per_record` sends one request per record.
- **Authentication**: Bearer token, API key header, and basic auth forwarded
  with each delivery request.
- **Platform-formatted payloads**: `slack` and `teams` types send pre-formatted
  Slack Block Kit and Microsoft Teams Adaptive Card payloads automatically.
- **Test delivery**: Verify endpoint reachability and authentication before
  attaching a webhook to a live resource.
- **Delivery history**: Inspect per-dispatch outcomes, HTTP status codes, and 
  error messages for any job or event monitor.

## ED score filtering, entity attributes, and event monitor timezone

Refines Company Monitors with relevance threshold control and richer entity 
data in results; adds timezone support for event monitor scheduling.

**Features:**

- **ED score filtering**: Submit jobs with `ed_score_min` to exclude connected 
  entities below a relevance threshold. Only records where at least one entity 
  meets the minimum score are returned.
- **Entity attributes in results**: Each matched entity in `connected_entities`
  now includes a `type` field and a `company` object with domain, alternative
  names, and key persons.
- **Event monitor timezone**: Set an explicit IANA timezone on event monitor creation with
  the new `timezone` parameter. Used as the fallback when the schedule string
  does not include one. Defaults to `"UTC"`.

**Changed:**

- [`POST /catchAll/datasets/{dataset_id}/entities/list`](/web-search-api/api-reference/datasets/list-entities-in-dataset)
  replaces `GET /catchAll/datasets/{dataset_id}/entities` for listing entities.
  Pagination and filter parameters are now accepted in the request body.
- [`POST /catchAll/datasets/upload`](/web-search-api/api-reference/datasets/create-dataset-from-csv)
  and
  [`POST /catchAll/datasets/{dataset_id}/upload`](/web-search-api/api-reference/datasets/upload-csv-to-dataset)
  now require a `domain` column. A missing column header returns `422`. Rows
  where `domain` is empty are skipped and reported in `validation_report`.

</Update>

Introduces job and event monitor deletion, event monitor execution history, resource sharing, 
and filtering by ownership across all list endpoints.
